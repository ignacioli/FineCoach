## 宿主实际流程（仅专用虚构 AVD）

每个 AVD 都 fresh install：先卸载 test package 和 app，再安装本轮两个 APK；不在负责人数据安装或实体设备上执行以下清理。宿主从 android/ 构建 `./gradlew assembleDebug assembleDebugAndroidTest` 并记录 digest，安装流程为：

```sh
adb uninstall com.ignacioli.finecoach.test
adb uninstall com.ignacioli.finecoach
adb install -t app/build/outputs/apk/debug/app-debug.apk
adb install -t app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
```

每次只针对指定专用 AVD；宿主脚本选择目标 emulator，本文不写 serial。fresh install 后先记录 package alarms=0，避免旧行、alarm 或 reboot handoff 混入证据。

API 31 没有 runtime POST_NOTIFICATIONS 对话框：`adb shell appops set com.ignacioli.finecoach POST_NOTIFICATION allow` 仅重置此前 appops 实验阻挡，不能代替系统通知总开关。打开 `android.settings.APP_NOTIFICATION_SETTINGS`，extra `android.provider.extra.APP_PACKAGE=com.ignacioli.finecoach`；用 uiautomator dump 定位 `com.android.settings:id/main_switch_bar`，读取 `android:id/switch_widget` 的 checked 状态，根据总开关 bounds 中心执行 input tap，并重新 dump 确认。允许→拒绝→恢复依次为 checked=true→false→true；恢复后用 HOME 离开设置。

API 36 允许/拒绝通过 `pm grant` / `pm revoke com.ignacioli.finecoach android.permission.POST_NOTIFICATIONS` 配置。两级 API 的课程提醒 channel 保持开启；单独 channel-off 不属于这组已通过的自动化证据。

**不执行 `am force-stop`**：API 31 r6 已观察到它使 App 保持 stopped state，导致收不到 BOOT_COMPLETED；不能以此流程取代正常启动/重启证据。停止 emulator 前先 `adb shell sync`，刷新 guest page cache，避免硬停止丢失最后的 prefs/DB 写入。

公共 runner 为 `com.ignacioli.finecoach.test/androidx.test.runner.AndroidJUnitRunner`，类为 `com.ignacioli.finecoach.AppointmentReminderDeviceTests`。逐方法执行形式为：

```sh
adb shell am instrument -w -r -e class com.ignacioli.finecoach.AppointmentReminderDeviceTests#METHOD -e appointmentPermissionState STATE com.ignacioli.finecoach.test/androidx.test.runner.AndroidJUnitRunner
```

| 顺序 / method | 配置与证据 |
|---|---|
| 1. `grantedSaveRegistersAlarmAndDeliversPublicTimeOnlyNotification` | 通知允许、SCHEDULE_EXACT_ALARM appops allow；STATE=granted；保存、registry/OS alarm、触发后的通用通知正文与 PUBLIC visibility |
| 2. `deniedSavePersistsWithoutDeliveringNotification` | API 31 Settings 总开关关闭；API 36 revoke POST_NOTIFICATIONS；STATE=denied；保存仍成功且无投递 |
| 3. `revokedExactAlarmAccessUsesWindowFallback` | 恢复通知允许，SCHEDULE_EXACT_ALARM appops deny；STATE=granted，额外 `-e appointmentExactAlarmState revoked`；registry `\|false`、OS alarm、正 window 时长且无 permission exact reason |
| 4. `prepareBeforeReboot` | 恢复 exact allow，STATE=granted；保存次日预约及 UUID/trigger/boot count handoff，成功才保留数据 |
| 5. `assertRestoredAfterReboot` | 两方法间执行 adb reboot，等待启动完成及 credential storage 可用；不先启动 App 或运行 reconcile；STATE=granted；直接核对 Room、boot count 与 OS alarm，随后清理自建数据 |

每方法均以非空 instrumentation 文字 `OK (1 test)` 取证，不能只看 adb exit code。dumpsys 不打印 Intent identifier；以 package + action tag + 预约的 origWhen epoch 唯一匹配完整 record，不仅匹配 package 或 PendingIntent token。fallback 接受实际 `window=+10m0s0ms`，拒绝 `window=0` / `exactAllowReason=permission`；超时诊断仅附 package alarm 调度 metadata。创建后的失败路径清理自建学员/预约，仅成功 prepare 保留至 reboot assertion；后者即使失败也清理。
