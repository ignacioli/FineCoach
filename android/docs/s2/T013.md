## 实现

所有 Appointment mutations 在 generation-bound Room transaction 中重新读取状态与冲突。开课与 session pointer / 双向关联同一 transaction；放弃空 Session 与安排 scheduled、解除关联同一 transaction；完成 Session 与安排 completed 同一 transaction。正常完成的扣课由现有 FinishSessionUseCases/CreditUseCases 的 `sessionComplete` event key 执行，结果与 Session durable completion 分开返回；无关联训练保持原 adhoc 选择。

缺席遵循 iOS：先持久化 absent/choice，随后通过已有 CreditUseCases 扣课。`AbsentAppointmentResult` 明确返回 appointment 与 settlement 两部分；无课包返回 null adjustment，扣课失败返回 Failure，不能据外层 Success 宣称扣课成功。相同缺席选择重复提交可恢复扣课，sourceEventKey 防重扣；取消不扣课，删除必须 confirmed 且满足 domain future boundary。

## 与 spec / iOS 的差异

- S2-D06 / FR-007a 是与 iOS 的有意差异：iOS `AppointmentUseCases.swift:456-475` 会复用已关联 A 的训练再关联 B，结算只取 first（`CreditLedgerUseCases.swift:390-393`）；Android 返回明确的 `PreviousTrainingNeedsHandling(A.id, session.id)`，B 仍 scheduled，所有数据不变。教练先正常结束/放弃旧训练再开始 B。未关联任何安排的临时训练仍沿用 iOS 复用并关联。
- 逾期规则见 T010（iOS 以结束时间判定）。
- 本次及以后保留 iOS 原 termination；repeatCount 不减去过去次数，而是从 boundary 重新展开原 count；保留原 detached/resolved 实例，boundary focus 只改边界实例，其余沿原逐次 focus。API 不开放 intervalDays 变更（FR-005 的限定字段）。
- 缺席扣课失败不回滚缺席状态，来自上述 iOS 明确行为；扣课失败被显式返回，不吞错误。

## S2-D06 已落地（FR-007a，2026-11-17 续跑 2）

负责人裁决来源：`.handoff/decisions/android-port.md` S2-D06；批准 spec 的 FR-007a。`AppointmentUseCases.startTraining` / port 现在返回 `ApplicationResult<AppointmentTrainingStartResult>`：

- `Started(session)`：正常创建或复用未关联安排的训练，完成 B ↔ Session 关联。
- `PreviousTrainingNeedsHandling(appointmentID, sessionID)`：对应「需先处理上次训练」，携带 A 的 UUID 和 SessionID，供 Phase 5 可见入口进入旧训练；这是可区分的领域结果，不是通用 conflict。

为满足零写入，`AppointmentRepository.start` 在同一个 generation-bound Room transaction 内、调用可能修复 active pointer 的 `startOrOpenInTransaction` **之前**只读检查该学员 active Session 的安排关联。若关联其他安排，则立即返回上述结果；不修 pointer、不创建/关联训练、不改 A/B/Session/ledger。不新增自动结束、扣课或放弃。正常完成 A 时仍通过既有 FinishSessionUseCases 按 sessionComplete 扣一次；正常放弃空训练时 A 回到 scheduled，之后 B 可新建训练。schema、DAO、S1 开课/结算实现均无本轮改动。

Phase 5 / T041 的提示和「进入上次训练」可见按钮尚未实现，领域结果已准备好。本项没有剩余的产品裁决。
