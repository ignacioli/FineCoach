## 完成与扣课的边界

1. iOS `ActiveSessionViewModel.swift:842` 先调用 `ActiveSessionUseCases.finish`，成功后才调用 `settleCredits`；`CoreDataSessionRepository.swift:94` 将 terminal Session 与临时动作 claim 释放作为一次写入。Android 调用既有 `SessionRepository.complete(settleCredits=false)`，同一 Room transaction 完成 Session / revision / pointer 释放 / session-only claim 释放。时长 checkpoint 与显式丢弃未完成组先分别保存；完成写失败后仍保留 inProgress，不尝试扣课。调用方复用同一个 `ActiveSessionUseCases` 才能保留失败保存状态；T009 检查 Failed / Saving，避免 finish 覆盖尚待重试的输入。
2. 完成成功后结算才开始，**不与 Session 完成合并为同一事务**。`FinishedSessionResult.session` 说明已完成，`settlement: ApplicationResult<SessionCreditOutcome>` 独立说明选择待处理 / 无包 / 不可用 / 失败。外层 Success 只表示完成已持久化，调用方必须检查 settlement，不能据此外层结果宣称已扣课。
3. S1 全部为 ad-hoc，没有 Appointment 自动扣课。可用包返回 `AdhocChoiceRequired`，显式 `debitAdhoc` 才调用冻结 `CreditUseCases.debitOnAdhocSession`。跳过或取消不写 ledger；结束前退出、完成后选择前退出，重新加载仍不会自动扣课。无 active 包单独保存 coach-only `noActivePackage` 注记，失败作为 settlement Failure 返回，允许重试。过期 / 0 余额返回不同 `PackageUnusable` reason，可显式跳过；手工调整沿用 T007 用例，不在本任务新增 UI 或绕过非负余额检查。
4. `CoursePackageRepository.kt:286` 在写事务内先查 sourceEventKey，再重算 ledger balance、检查非负余额、写 adjustment 与 balance cache。重复 / 并发确认均复用 `adhocSession(sessionID)`，至多一笔扣减；cache 更新失败应整笔回滚。扣课失败保留 completed Session，显式 Failure 返回；调用方重试 `debitAdhoc`，不重复完成训练。
5. `settlement` 先查该 Session 的既有 ad-hoc ledger，再查当前包，因此已扣过且余额耗尽也返回真实原 adjustment，而不是误报新扣课失败。扣课确认前重新获取当前包并校验 coach 看到的 package ID；包替换则 conflict，要求重新选择。余额最终检查仍在 T007 的实际写事务内。
6. 历史 Repository 在 transaction 内投影，只列 completed、有 completedAtUTC 且至少有一个 completed 组的记录。窗口为包含今天的最近 7/30/90 个本地日历日，按明确 `ZoneId` 比较，按 `Instant` 降序而非 SQLite TEXT 字典序。训练重点为 ANY overlap，与动作 / 学员 / 日期条件做 AND；动作按 sourceID 的 snapshot 关联，不依赖 catalog 当前名称。detail 保留原组状态，statistics 仅由 completed 组计算，pending/draft 不算有效训练。清除筛选保持学员范围。
7. 总结保存调用冻结 `saveCompletedSummary`；历史编辑仅调用 `updateTrainingFocus`，保持 Session / Student 身份、完成时间及子内容，不接入任何结算函数。失败返回原 ApplicationResult，输入 command 由调用方保留重试；stale revision 不覆盖。actionPrivateNote 只读保留，未增加编辑入口。注记不改变训练 revision，匹配 iOS `recordCreditSettlementNote` 的独立存储行为；notes 不构成 share/export DTO。
