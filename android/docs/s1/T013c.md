## 2026-11-09 DEVICE 失败修复（基线 1b7b3d4）

本轮只改 `src/androidTest/.../RestNotificationPermissionTests.kt`、`RestNotificationNavigationTests.kt`，新增纯测试辅助 `RestNotificationDeviceSupport.kt`，以及本运行说明；**产品代码零改动**，不 git add、不 commit。

### 根因：证据与未确认部分

1. **撤权导致同进程 instrumentation 退出**：API36 原日志在 `actualPermissionGrantAndRevoke…` 内返回 `shortMsg=Process crashed`；测试第一步就是在目标进程内 `pm revoke POST_NOTIFICATIONS`。AOSP PermissionManagerServiceImpl 的默认 `onPermissionRevoked`（351–373）安排 `killUid`，普通撤权不带 test-only overrideKill；平台机理已证实。该崩溃与此机制吻合，但原日志未附 system_server 的实际 kill reason，因此当前设备的直接死亡原因仍是高置信推断，而非 logcat 复现。改为宿主在 instrumentation 启动前设置权限；测试完全不 grant/revoke。
   来源：[AOSP permission callback](https://android.googlesource.com/platform/frameworks/base/+/cb6e89afc2aef497388f83ebe70c7a7c6cd5f55f/services/core/java/com/android/server/pm/permission/PermissionManagerServiceImpl.java)。
2. **通知立即查询不构成完成屏障**：API31 在 cancel 后立即 assertFalse 失败；API32 的 permission 类实际日志是发送后立即 single 抛 NoSuchElement；API31 的 navigation 类也在发送后立即 single 失败。AOSP NotificationManagerService 将 enqueue/cancel 排到 worker handler，Binder 调用返回不表示 posted/removed 状态已经可见。因此原测试存在确定的同步缺项。是否这完全解释每次“未出现”，原日志无法证明；新测试先严格检查 enabled，再等实际系统状态，仍未出现会明确超时失败。
   来源：[AOSP async notification/cancel](https://android.googlesource.com/platform/frameworks/base/+/bcd836519713103fede1455a52e1deaa43548edb/services/core/java/com/android/server/notification/NotificationManagerService.java)。
3. **Accessibility ID 前提与事件时序**：产品 `S1App.kt` 已在 NavHost subtree 设置 `testTagsAsResourceId=true`，目标 Box 已有精确 `active-destination-ID` tag。原测试却没有设置 UiAutomation `FLAG_REPORT_VIEW_IDS`；本机官方 SDK API36 `android/accessibilityservice/AccessibilityServiceInfo.java:279-285` 明确该 flag 请求报告 source view ID，默认不设置；`AccessibilityNodeInfo.java:2198` 也要求 client 设置它。Compose 官方文档要求 subtree 的 testTagsAsResourceId，且按原 tag 查询、不拼 package:id 前缀。现在测试显式开启并读回核对 flag，finally 恢复原 flags；同样只按精确 tag 匹配。改为查询树的最终状态，不依赖某一次窗口事件恰好发生在节点可见后。API36 和 API32 原日志都能看到 MainActivity 窗口但首次导航等待超时；API31 首次通过。**各次运行的原始 service flags / node tree 缺失，不能断言这是 API36 独有行为，也不能仅凭 API31 一次通过推翻该配置要求。实际版本差异和这两项修复的设备效果待宿主复跑。**
   来源：[Compose interoperability / UiAutomator](https://developer.android.com/develop/ui/compose/testing/interoperability#interoperability-with-uiautomator)。
4. **“前台抑制 a”不是现有实现的解释**：Android `notifications/RestNotifications.kt:47-59` 的 receive 仅检查 payload/deadline、pending metadata、permission/channel enabled，没有 foreground / visible Student 判断。iOS `ios/FineCoachApp/App/RestNotificationRouting.swift:72-81` 只对当前可见学员返回空 presentation options，对其他学员返回 banner/list/sound；`:222-234` 在 willPresent 使用该判断。原用例打开 b 后发 a，正好应允许 a 的系统提醒。因此不改变产品策略，也不退到桌面来掩盖此场景；保留前台 b → a 通知 → a 原 Session 的验证。

### 系统状态等待合同

`RestNotificationDeviceSupport.awaitSystemState` 使用单个 ScheduledExecutor 每50ms只读一次系统状态，最多15秒；条件满足即结束，超时或读取异常即失败，finally 取消任务并关闭 executor。没有 Thread.sleep/SystemClock.sleep，也没有业务重试。`notify/receive`、单次取消、PendingIntent.send / startActivity 都在等待器外，各阶段只执行一次；清理阶段的取消不被用作使断言通过的重试。

- 通知发送后等待指定 tag + id=0 恰好一条，仍严格核对通用标题/正文。
- 取消后等待该 tag + id=0 消失，并核对另一测试 Session 的通知仍在；最后只清理两个测试专用 ID。
- 导航等待本 app accessibility tree 中精确目标 Session tag；不改成只检查 MainActivity、任意页面或文本。
- 用已到期的测试 adapter request 驱动系统 notify，与原测试方式相同；此证据不覆盖 AlarmManager 的 inexact 实际投递时延。
